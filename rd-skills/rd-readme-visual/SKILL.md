# README Visual

Write, restyle, or audit a project `README.md`: the page a developer reads to
decide whether to try the project at all. A README made with this skill is also
proof that the project works: it carries real screenshots, short GIF/WebP demos
and animated SVG diagrams, all generated by the agent by running the actual
project with real tools. An existing README is diagnosed first, so a rewrite
fixes what is actually broken.

Every README keeps one rich structure: a centred top block, Iconify section
headings, tables, an ASCII tree, collapsible `<details>` cards for advanced
material, GitHub alert hints, a tailored license block, and generated media.
The look is not fixed. The layout, palette, header, icon set, badge set, section
names and signature sections are chosen per project, using the reference READMEs
at the bottom of this file as inspiration, never as templates.

## Task modes

| Mode | When | What to do |
| --- | --- | --- |
| **Create** | No README, or a plain one | Full workflow below |
| **Restyle** | README exists, content is fine | Keep the wording; rebuild visuals to the required structure |
| **Add a section** | New feature or area to document | Pick the shape from the section menu; place it where the reader expects it |
| **Metrics / dashboard** | Counters, charts, repository activity, installs, downloads, quality or project trends | Inspect the real project and apply `references/live-metrics-badges-charts.md` and `references/shieldcn/dynamic-data-and-metrics.md`; derive useful metrics and generate data pipelines when necessary |
| **Review** | "Is this README still right?" | Score it against `references/audit.md`, verify every claim against the code, list stale or missing sections with proposed edits, run the validator. No rewrite unless asked |

## Workflow

1. **Inspect** (§1) the repo: entry points, config, assets, screenshots, existing
   README, license, dependencies, platforms, and what the project can actually show
   (output, UI, flows).
2. **Diagnose** (§2) in restyle and review modes: score the existing README and
   verify every claim against the code before editing anything.
3. **Ask** (§3) only the concrete questions the repo can't answer.
4. **Style** (§4): choose the layout from the reference READMEs and the accent colour.
5. **Produce media** (§5): run the real project and generate the screenshots,
   GIF/WebP demos and animated SVGs with real tools, then look at every file.
   The standard pipeline (banner, recording, map, badges, icons) is `references/pipeline.md`.
6. **Discover metrics** when useful or requested: inspect the project for measurable capabilities, usage, quality and growth, then follow `references/live-metrics-badges-charts.md`. Only add data-backed counters/charts and create the necessary repository-specific collector/Action for custom metrics.
7. **Draft** (§6) the required structure, filling sections from
   `references/section-menu.md` and embedding the generated media.
8. **Writing pass** over the copy (`references/writing.md`).
9. **Validate and look** (§7): run the validators, fix what they report, then render
   the page and view it.
10. **Close** by asking: "Anything else to highlight or include that I might have missed?"



## Original motion, generative SVG and authentic demonstrations

When designing SVGs/GIF/WebP, **never default to generic AI decorative graphics**. Inspect the repository's actual UI, data flows, CLI output, art direction and distinctive terminology. First use `references/motion/art-direction.md` to derive a purpose-specific composition. Follow `references/motion/animated-svg-design.md` for SVG motion, `references/motion/animated-demos.md` for actual program recordings, and `references/motion/dynamic-svg-generation.md` for data-backed regeneration. See `references/motion/motion-design-recipes.md` for authored composition grammars and `references/motion/readme-forge-patterns.md` for reusable block architecture. Preserve existing `references/media.md` for original VHS/Asciinema/ffmpeg workflows.

**Media decision:** (a) use real screenshots or captures to prove actual program behavior; (b) use original illustrated SVGs to explain verified architecture; (c) use data-driven SVGs only with true data and provenance. Never label an illustrated terminal as a real recording. Provide static frames and respect `prefers-reduced-motion`.

**Original generators** (stdlib except Pillow video):
- `python3 scripts/generate_motion_svg.py --config templates/motion/signal.example.json --style signal --output assets/readme/signal.svg`
- `python3 scripts/generate_motion_svg.py --config templates/motion/signal.example.json --style terminal --output assets/readme/terminal.svg`
- `python3 scripts/generate_motion_svg.py --config templates/motion/signal.example.json --style orbital --output assets/readme/orbital.svg`
- `python3 scripts/generate_motion_svg.py --config templates/motion/signal.example.json --style signal --static --output assets/readme/signal-static.svg`
- `python3 scripts/render_motion_frames.py --config templates/motion/signal.example.json --output assets/readme/flow.webp --fps 12 --seconds 3` (illustrated animation, not an application capture; requires Pillow)
- `python3 scripts/check_motion_svg.py assets/readme/signal.svg` then visually inspect GitHub's rendering

**Composition architecture:** apply the reusable-blocks and global-variables concepts from [SenaThenu/readme-forge](https://github.com/SenaThenu/readme-forge) without copying its code or misrepresenting it as a motion renderer. Use project-specific palette, exact labels, real links and generated assets as composable README building blocks. Source notes and attribution boundaries: `references/motion/provenance.md`.

**Quality gate:** Is the main message visible without animation? Are labels sourced from code/docs? Does any element move without communicating state or flow? Is the composition recognisably specific to this project? Is the result legible at 375px? If any answer fails, revise or omit the animation.

## ShieldCN visual design system (expanded)

This skill is not limited to badges. When the task involves README visual identity,
headers, banner assets, joined groups, responsive layout, counters, contributor
walls or charts, load `references/shieldcn/overview.md` and only the relevant
focused references under `references/shieldcn/`.

**Visual workflow**:
1. Inspect repository content, branding, source images and the existing README.
2. Choose a visual composition based on project type, not merely on available API endpoints; see `references/shieldcn/readme-layouts.md`.
3. Choose or create a shared palette JSON (`presets/white-yellow-outline.json`, `presets/lastfm-red.json`, or `presets/zinc-minimal.json`). Honour the user's requested colours rather than substituting different accents.
4. Generate URL/HTML assets with `scripts/shieldcn_visual.py`; it supports `badge`, `dynamic`, `header`, `group`, `chart`, `contributors`, `sponsors` and `views`. Build hero fragments with `scripts/compose_readme_hero.py` and `templates/hero.example.json`. The existing generators (`shieldcn_badge.py`, `generate-header.py`, `generate-badge-row.py`) remain available.
5. Use repository-specific collectors and the existing `references/live-metrics-badges-charts.md` for measured numbers and historical charts; do not invent counters or chart history.
6. Preserve meaningful README text, existing links, stable section anchors, screenshots and working commands. Integrate new visual elements only where helpful.
7. Audit via `scripts/audit_visual_assets.py` (optionally `--remote`), `scripts/validate-readme.py` and `templates/visual-checklist.md`. Render in GitHub light/dark and narrow layouts. Vendor essential external images with `scripts/cache_visual_assets.py` if reliability is required.
8. Disclose unverified remote rendering, third-party caching, unavailable provider data or any static placeholders.

**Reference routing**:
- Header/banner presets, custom images, typography: `references/shieldcn/headers-and-banners.md`
- Badge variants, split controls, colour interactions: `references/shieldcn/badge-design-system.md`
- Joined groups and multi-row badge layouts: `references/shieldcn/groups-and-composition.md`
- Charts, current GitHub star-history support, remote series: `references/shieldcn/charts-and-visualizations.md`
- Counters, installs, file statistics, view counters: `references/shieldcn/dynamic-data-and-metrics.md` and `references/live-metrics-badges-charts.md`
- Supported provider discovery: `references/shieldcn/provider-catalog.md`
- Section icons, Iconify and logo assets: `references/shieldcn/icons-and-logos.md`
- GitHub-compatible layout, `<picture>`, contrast and mobile: `references/shieldcn/responsive-and-themes.md`
- Templates and end-to-end README patterns: `references/shieldcn/readme-layouts.md`, `references/shieldcn/branding-and-templates.md`, `references/shieldcn/presets-and-recipes.md`
- Contributor and sponsor walls: `references/shieldcn/sponsors-and-contributors.md`

**Do not confuse** ShieldCN image fetches with human visitors, published
skills.sh install counts with locally installed skill directories, or source-file

## Terminal-window recipe (reproducible pipeline)

A repeatable way to give any repo a calm, owner-styled README: a dark terminal-window banner with the
owner's wordmark, one real terminal recording, an optional animated hub-and-spoke map, badges with measured
counts, and accent-coloured heading icons. Full walkthrough, per-repo-type choices and the pitfalls learned:
`references/pipeline.md`.

1. **Colour from the logo**: `scripts/palette.py assets/icon.webp` gives the accent and a text-safe variant. With
   no logo, or a black-and-white one, **ask the owner** (offer two or three hexes). Never guess.
2. **Banner**: `scripts/header.py --wordmark … --accent … --subtitle 'a|b|c' --command … --listing …`. A flat
   dark window, the owner's wordmark with an accent silhouette shadow, white subtitle with accent dots, a typed
   command with its real listing. No wordmark: a text `--title` works for any repo. Keep it calm.
3. **Recording**: `scripts/make-tape.py` (Ghostty colours, minimal prompt) then `scripts/record.sh`
   (2x, cropped, evenly padded, window bar, lossless animated WebP). One real command, summary lines only,
   frames viewed and free of personal data.
4. **Map**: `scripts/flow.py config.json` (`references/flow-example.json`) when many things read one thing.
   Illustrated, so never call it a recording.
5. **Badges**: the owner's style, counts measured from the repo, every anchor real; replace placeholder counts.
6. **Headings**: one or two plain nouns, Lucide icons via the slash form in the accent.
7. **Wire it up**: `templates/build-media.sh.tmpl` becomes `assets/build-media.sh`; validate with
   `validate-readme.py --online` and `check-media.py`; seek-check every animated SVG; report what could not be
   checked (GitHub's renderer, light theme, phone width).

## 1. Inspect

Gather facts so the questions you ask are few and specific:

- Entry points (`bin/`, `src/`, `cmd/`, `main.go`, `package.json`, `Cargo.toml`, `pyproject.toml`)
- Config files and examples (`config.example.json`, `.env.example`)
- Visual assets: icons, headers, screenshots, GIFs (`assets/`, `contents/`, `docs/`, `data/`)
- Existing README: keep accurate content and the user's own wording where it is good
- `LICENSE`: which license, and whether it is already tailored to the user
- Platforms, runtimes, integrations, test commands

## 2. Diagnose

Skip on a new README. On an existing one, score it before changing a line: a
rewrite that fixes the prose and keeps a broken install has fixed nothing, and in
Review mode diagnosing is the whole job.

1. **Read it cold.** Note where you personally got confused. Your first-read
   confusion is the closest thing to a new reader.
2. **Run the mechanical check** (§7) for structural facts: heading tree, missing
   alt text, broken links, a missing Quick Start.
3. **Verify every claim** against the code: each command, flag, default, env var,
   path, and version requirement, plus any performance or "production ready"
   claim. This is the check that catches the most real damage, because a reader
   who hits a broken install leaves and does not file an issue.
4. **Score it** against `references/audit.md` and print the scorecard with
   evidence before proposing edits. The owner can reject a diagnosis, so give
   them one to disagree with.

Present the fix list ordered by return per hour spent, not by how easy it is to
write; that ordering puts the honest status line and the working install path
first and the badge row nearly last.

## 3. Ask

Ask about concrete things, never abstract ones like "vibe" or "feel". Good
questions name real files, colours, and sections, and have a recommended
answer. Ask only what the repo can't tell you, in one short round, and state
your default for everything else. See `references/interview.md`.

Typical questions:

- Which colour to use. Colour comes from the repo's logo or icon: sample its dominant colours and use them for
  the shieldcn badges, the header accent and the Iconify icons. When the repo has no logo or icon and you are
  unsure, ask which accent to use and offer two or three concrete hexes (for example from the owner's terminal theme)
- Which image to use as the header logo when there are several
- Whether to add screenshots or GIFs, and where they are
- Which license block (offering the variants that exist for the repo's license)
- Whether to keep or rewrite existing copy the user wrote

## 4. Style

There is no default layout. Open the reference READMEs at the bottom of this file,
pick the one or two closest to the project (by kind of project and by how much
there is to document), and borrow ideas from them: the top block, the section
order, how a big reference folds into dropdowns, how screenshots are laid out. They
are inspiration, not templates. Two different projects should not end up with the
same README skeleton.

Decide these, and state the choices in two or three lines before drafting:

| Decision | Options |
| --- | --- |
| **Top block** | shieldcn header banner (presets `grid`, `graph`, `dots`, `glow`, `gradient`, `surface`), a project icon beside an `<h1>`, a banner image, a typing-SVG tagline under either |
| **Badge row** | one row of 3-5 shieldcn `outline` badges, adaptive `<picture>` pairs, classic shields.io, or none when no badge verifies anything |
| **Icons** | Lucide, another Iconify set, or readmecodegen; one set per README, in the accent colour |
| **Density** | short (a small tool) up to a full documentation README (a large application): whatever the repo needs |
| **Signature sections** | demo recording, screenshot grid, animated SVG workflow or architecture diagram, Mermaid diagram, Compatibility, Use Cases, FAQ |
| **Toolbox** | `references/shieldcn-recipes.md` for modern headers and badges; `references/local-visual-archetypes.md` when matching an older repo family (mp3tag, zsh, clipped, KB) |

Rules that hold in every layout:

- **Top block, usual order**: identity first (a banner or title carrying the name and
  a short subtitle), then one row of 3-5 clickable badges, then the bold
  one-sentence summary, then a pipe-separated nav bar (`Quick Start | Usage | … |
  License`). A layout may reorder or drop a piece, but the name and the one-sentence
  summary always come before anything a reader must scroll past.
- **Headings**: one Iconify icon per `##`, in the accent colour.
- **Accent**: one accent colour for badges, header and icons, taken from the repo's logo or icon. With no logo
  or icon, ask the owner rather than guessing. Derive a small role palette from it (accent, a second accent,
  surface, muted text), the way open-design's `brand-extract` names palette roles, and lighten the accent for
  small text so it keeps contrast on the dark surface.
- **Header**: always dark. Use a shieldcn header with `mode=dark`, or a custom dark SVG (the owner's wikimedia
  banner is a `#09090b` card with a faint grid). Never an adaptive light/dark pair. Be creative: the whole banner
  can be one terminal window running a real command (`references/media.md`, Creative SVG recipes). Animate it
  only when the motion earns its place (§5).
- **Badges**: be creative, as in the owner's READMEs: real brand logos, one accent, two-tone label and value
  (wikimedia), for-the-badge shields with `custom-icon-badges` for logos shields lacks (lastfm-scrobbler), outline
  badges in one theme (perkolator). Every badge must still be true (`references/badge-gallery.md`).
- **Section names**: one or two words in Title Case (`Quick Start`, `Usage`,
  `Configuration`, `Structure`, `Development`, `License`). Prefer plain nouns (`Overview`, `Functionality`,
  `Architecture`, `Compatibility`); avoid phrases and questions such as `How It Works` and `Why This Repo`.
- **Complete, with no length rule**: the README is the project's documentation, so its
  length is whatever the repo needs. A small tool is short; a large application like
  audio-agent is a long README because every item has to be documented, explained and
  shown. Cover everything the repo has, each as its own `##` section where it applies:
  Quick Start, Installation (every install method and the external tools with what
  needs each), Compatibility (systems, runtimes, formats, integrations), Use Cases ("I
  want to … → run"), Workflows (diagram plus a steps table), Usage (modes and shared
  options), one section per feature area, Commands, Configuration (every setting), How
  It Works (architecture, guarantees, state, decisions), Troubleshooting (one dropdown
  per symptom), FAQ, Structure, Development, License. Nothing is moved out of the
  README to make it shorter; `docs/` is for generated references (like a full command
  list) that the README links to.
- **Visually pleasing at any length**: lead sentence or two, then real example code,
  then tables (a "who wins" or "what each does" table beats paragraphs); long
  explanations, full references, state files and decisions go in `<details>` so the
  page scans. Mermaid diagrams for workflows and architecture.
- **Concise titles**: every `##`, `###` and `<details>` summary is a short proper title
  in Title Case ("Hard Albums", "Plans and Undo", "Lucida Setup"), never a sentence or
  a colon list ("Matching a hard album: ISRC, AcoustID, …"). Troubleshooting summaries
  name the symptom in a few words ("Slow First Run", "Agent API Error").
- **Icons everywhere a reader scans**: every `##` and `###` heading and every
  `<details>` summary gets a Lucide icon in the accent colour, sized to the text it sits
  with and centred on it with `align="absmiddle"` (GitHub keeps the attribute; without it
  an icon rides above the line): `height="24"` for `##`, `20` for `###`, `14` in a
  summary, a table cell or running text. Group a big section's dropdowns under a
  `### Reference` heading instead of a loose run of them.
- **Coloured brand icons in tables**: wherever a table names services, providers,
  sources, tools or integrations, put the brand's own coloured icon (16 px) before the
  name, always next to the name (never icons alone). Where to get them, in order:
  0. Wikimedia Commons for the real brand mark (most accurate): `scripts/commons-icon.py
     search "Discogs icon" --md` lists matching SVGs with size and licence, `url
     "File:ITunes logo.svg"` prints one file's address (`--png 64` for a PNG rendering),
     `get … --out assets/icons` downloads it. Also installed as `commons-icon`. Prefer
     square icons over wide wordmarks; credit CC BY-SA files if you ship the file itself.
     Link the **PNG rendering** (`--md` gives a 120 px one), never the SVG original:
     GitHub's camo image proxy gets HTTP 502 from Commons SVG originals but loads its PNGs;
  1. the owner's repo `https://github.com/deathrashed/iconography` via jsdelivr
     (`https://cdn.jsdelivr.net/gh/deathrashed/iconography@main/<path>`; search its tree with
     `gh api "repos/deathrashed/iconography/git/trees/main?recursive=1"`), which has
     things the public sets lack (deemix, lucida, slskd);
  2. the dashboard-icons MCP (`match_icons` with `include_details=true`) for exact
     dashboard-icons, selfh.st, LobeHub and Simple Icons CDN URLs;
  3. Simple Icons with a colour (`https://cdn.simpleicons.org/<slug>/<hex>`);
  4. the site's favicon (`https://www.google.com/s2/favicons?domain=<site>&sz=64`),
     checked against the generic globe; else a coloured Iconify glyph that fits.
  Check every icon URL returns an image, and look at the rendered page in dark mode:
  a black mark disappears there, so use a grey Simple Icons colour, the set's `-light`
  variant in a `<picture>` pair, or a favicon on its own tile.
- **The GitHub image check**: every README image reaches readers through GitHub's camo
  proxy, which refuses some hosts and formats even when the URL works in a browser.
  Render through `gh api markdown -F text=@README.md -f mode=gfm`, pull every
  `src="https://camo…"` and request each one; any non-200 image will be blank on GitHub.
- **Iconify checks**: Iconify rate-limits bursts (HTTP 429), so check Lucide names against
  `https://cdn.jsdelivr.net/npm/@iconify-json/lucide@latest/icons.json` (icons and aliases)
  instead of hammering the API, and prefer current names (`circle-question-mark`, not
  `circle-help`). The validator's "keep to 1-2 accents" warning does not apply to brand
  icons and their stand-ins.
- **Alerts**: two or three in the whole README.
- **Ship a demo when the project has visual output**: a CLI gets a `vhs` recording
  of one real flow, an app gets screenshots, a UI gets an animated WebP. Produce
  it, do not just link to it. Formats, tooling and the `<video>` trap that renders
  as a blank gap: `references/media.md`.
- **Status is stated**: one line saying experimental, beta, stable, or seeking
  maintainers. Only 21.4% of READMEs carry any (Prana et al. 2019, 393 repos), so
  it is rare and costs one sentence. Never write "production ready" without
  evidence a reader could check.
- **Differentiation earns its place**: one short section naming the alternative a
  reader already knows and the concrete axis this wins on. Only 25.7% of READMEs
  have any (same study), and it is the scarcest content category there is.
- **Badges are assessment signals**: they must be backed by a check that cannot
  pass unless the fact holds (CI, coverage, version, license). An intent badge
  such as "PRs welcome" verifies nothing. Evidence base and the maintainer
  over-valuation: `references/audit.md`.

Private repositories: a raw.githubusercontent.com link from a private repo carries a
`?token=GHSAT…` that expires within hours (and must not be committed). Put the project's
own icon in the banner as a `data:` URI instead (shieldcn encodes it into the URL; nothing
is stored): a 96 px WebP at quality 80 is about 1.7 KB. GitHub's image proxy refuses
URLs past roughly 8 KB once it hex-encodes them (HTTP 414), so keep the header URL under
about 4,000 characters and run the GitHub image check on it. A `lu:`/`ri:` slug
(`logo=lu%3ASpeaker`) is the fallback when there is no icon.

## 5. Produce media

The media is part of the README and the agent makes it: run the real project, capture
what it really does, and embed the result. No mock-ups, no stock art, no screenshots
of a different tool, and no demo that was not actually captured. A README with
nothing to look at is a finding in its own right.

1. **Plan** from what Inspect found. Pick the smallest set that proves the project:

| Project | Generate |
| --- | --- |
| CLI | One `vhs` recording of the core flow as GIF or animated WebP, right after the summary; one more per major workflow when there are several |
| TUI or long-running process | `asciinema` recording rendered with `agg` |
| Desktop app or plugin | 2-4 window screenshots of different states (empty, populated, settings) in a grid, plus a short recording of one flow. With many screens, use the aligned three-column gallery from lastfm-scrobbler (`references/media.md`) |
| Web UI | Browser screenshots of the viewport content, light and dark when the UI has both, from the built-in browser or `agent-browser` |
| iOS or Android app | Simulator or emulator screenshots |
| Library, API or config repo | A real terminal recording of one call or of the check command, plus an animated SVG diagram of how the pieces connect |
| Any README with a workflow or architecture section | An animated SVG diagram authored from the real structure (names, directories, data flow), not decoration |

2. **Run it for real.** Build or install the project in a clean directory, use
   fixture or sample data, and capture. If it needs credentials, a service, or
   hardware you do not have, say so and ask for a recording; never fabricate output.
   No secrets, personal paths, usernames or real library data in any frame.
3. **Generate with real tools**, using the recipes in `references/media.md`:
   `vhs` (`.tape` to GIF/MP4/WebM), `asciinema` + `agg`, `screencapture` (macOS) or
   the platform's screenshot tool, the browser tools, hand-authored CSS-animated SVG
   checked with `rsvg-convert`, and `gifski` / `gifsicle` / `ffmpeg` to optimise.
   Verified on m3: vhs, asciinema, agg, gifski, gifsicle, ffmpeg, rsvg-convert and
   screencapture are installed; Playwright is not.
4. **Look at what you made.** Extract frames from every recording with `ffmpeg` and
   view them, open every screenshot, render every SVG. A frame with the wrong theme,
   a cut-off window, a stack trace or a personal path means redo it.
5. **Keep it regenerable.** Commit the sources (`.tape`, `.cast`, `.svg`) beside the
   outputs in `assets/`, and add one script or `just media` target that rebuilds all
   of it, so the next output change does not leave a stale demo.
6. **Budget.** Each GIF under about 5 MB, total media a few MB, prefer animated WebP
   inline and GIF only where the page must work outside GitHub. Animated SVGs honour
   `prefers-reduced-motion`, stay under about 20 KB, and carry `role="img"` and an
   `aria-label`. Never use `<video>` with a repo-relative or raw URL.

### Required structure

Build every README in this order:

1. **Centred top block** (its shape comes from the chosen layout, §4): `<div align="center">` with the
   shieldcn header banner, one row of clickable outline badges, the bold one-line
   summary, and a pipe-separated quick-nav bar. Every child carries its own
   `align="center"` (GitHub does not inherit it).
2. **Quick Start** within the first ~40 lines: requirements in one line, then a
   short code block from clone to first result.
3. **Generated media** (§5): a hero demo right after the summary or Quick Start,
   screenshots in a grid where the plan has them, and an animated SVG for the
   workflow or architecture, all produced with `references/media.md`. Every
   project with something to see has at least one real recording or screenshot.
   Never `<video>`.
4. **Core sections** with Iconify headings (Usage, Commands, Features,
   Configuration, and so on from the section menu), each built from tables and
   short examples rather than long prose.
5. **Advanced material in `<details>` dropdowns**: full flag lists, verbose
   config, platform-specific setup, troubleshooting, FAQ, internals. Bold
   summary line, blank line after `<summary>`, content that stands alone.
6. **GitHub alert hints** where they help: `> [!TIP]` for shortcuts,
   `> [!NOTE]` for context, `> [!IMPORTANT]` for requirements, `> [!WARNING]`
   and `> [!CAUTION]` for things that can lose data or publish publicly.
7. **Structure**: ASCII tree in a ```` ```text ```` block with `#` comments.
8. **Development / Building**: build and test commands.
9. **License**: tailored block from the gupload library (`references/licenses.md`).

Rules that hold in every style:

- **One palette**: badges, `logoColor`, Iconify heading colours, and typing SVG all use the chosen accent (optionally alternating with one secondary accent). Colours in query strings use `%23` for `#`.
- **Every `##` heading has an icon** (Iconify SVG or readmecodegen), never an emoji. One icon set per README.
- **Badges are clickable** (`<a>` wrapped) and link to something real.
- **Alt text** on every `<img>`, written for a person (`alt="Python 3 runtime"`).
- **Anchors resolve**: every `#link` matches a heading or `<a name>`. Headings with
  `&`, `:`, `?` or `'` produce anchors a reader cannot predict (`Run &amp; Test` is
  `#run--test`), so prefer `and` and plain words (`references/structure-and-links.md`).
- **Headings are one to three words in Title Case**, siblings share a pattern, and
  none is a sentence or a colon list (`references/structure-and-links.md`).
- **Link the thing, not the brand**: `[install uv](...)` not `[here](...)`. Nothing
  links to a `CONTRIBUTING.md` that does not exist.
- **Accurate content**: commands, flags, paths, and versions come from the repo, not from memory.
- **License matches the repo**: the block's license is the one in `LICENSE`, and that file carries the user's name.

## 7. Validate and look

```bash
python3 scripts/validate-readme.py README.md --online
python3 scripts/check-media.py README.md
```

Errors must be fixed. Warnings are judgement calls: fix them or say why not. `check-media.py`
also has to pass, and every image has to load through the GitHub image check (§4).

The validator can't judge appearance. Render the page and look at it before
calling it done:

```bash
gh api markdown -f text=@README.md -f mode=gfm -f context=OWNER/REPO > /tmp/readme.html
```

Open it (or the repo page) in a browser, check light and dark themes when
badges are adaptive, and check phone width. Outline badges drawn in only one
mode lose their labels in the other theme (`references/badge-gallery.md`).

Then run the cold-reader test (`references/audit.md`): five questions in 60
seconds, no context. A wrong answer names the check to fix, so it is worth
running even when no human reader is available.

## Live badges, counters and charts

For requests about dynamic badges, *any* counters, usage statistics, actual numbers, charts, growth and automation, **read `references/live-metrics-badges-charts.md`**. This covers skills and all other repo types: CLI commands, plugins, scripts, assets, docs, tests, releases, download numbers, platforms, features, packages, APIs, configuration, build status and project-specific metrics. Use bundled `scripts/repo_metrics.py`, `scripts/render_metric_badges.py`, and `templates/` as reusable building blocks, adapted to the actual repo; do not assume the repository follows a skills layout. Keep published registry installs, local installations, repo content counts, and view requests distinct. Do not fabricate statistics or histories.
